# UI Patterns

## Purpose

This file captures the preferred UI patterns for recurring product surfaces.

## Navigation

Primary nav should include:

- strong brand lockup
- compact core route links
- localization controls
- account actions
- mobile menu with the same information architecture

Preferred feel:

- precise
- premium
- calm
- slightly tactical

## Page headers

Every major page should have:

- clear page title
- one short descriptive line or status line
- optional key actions on the right

Dashboards should also expose:

- role context
- current system or verification state

## Dashboard shell

Preferred dashboard pattern:

- left sidebar or section rail
- top command header
- stat cards first
- primary content panes after

Dashboard pages should share:

- one stat-card style
- one side-nav style
- one table style
- one empty-state style

## Cards

Use cards for:

- listings
- dashboard panels
- profile blocks
- forms
- command sections

Cards should have:

- visible frame
- clear header/body/footer separation when needed
- restrained hover lift only when interactive

## Forms

Preferred form pattern:

- mono label
- clean input field
- strong focus ring
- consistent hint/error spacing
- grouped controls in logical sections

Avoid:

- scattered label positions
- inconsistent button placement
- overdecorated fields

## Tables

Use for:

- admin views
- operational lists
- orders
- bids
- verification queues

Preferred table characteristics:

- strong header row
- compact but readable spacing
- status badges aligned consistently
- row actions predictable and easy to scan

## Badges

Badges should communicate:

- status
- type
- classification
- system state

They should not be used as general decorative pills.

## Filters and search bars

Preferred pattern:

- one primary search bar
- grouped filters beneath or adjacent
- clear reset action
- visible active-filter state

## Modals

Use modals for:

- confirmations
- compact forms
- focused secondary workflows

Avoid using modals for:

- long multi-step flows
- large management interfaces that deserve full screens

## Empty states

Every empty state should include:

- a clear statement of what is missing
- a hint about what to do next
- a direct action when possible

## Alerts and feedback

Use consistent patterns for:

- success
- warning
- error
- informational states

Feedback should be short, clear, and operational.
